# shard v2 — the shape it ended with

v2 is the generation before this tree. It is deleted from `main` and kept at two git tags:
`v2-kernel-last` holds its kernel (`kernel/`), `v2-last` holds the rest (`std/`, `meta/`, `models/`,
`tools/`, `examples/`, `pins/`) and every document written up to the cleanup, the dated records
included. Paths below are at those tags: `git show v2-last:PATH`.

This page is what is carried forward from it: its shape, what it reached, and what was still good and
still bad when it stopped.

## 1. What v2 was

One small, total, first-order language doing three jobs: stating requirements, writing the algorithm,
and spelling what the hardware runs, through machine models written as ordinary libraries. Refinement
joins the layers (`impl ⊑ spec`: the implementation computes what the specification does, under stated
premises). Compiling is a theorem: untrusted generators emit a lower program together with
certificates (proof text the kernel checks), and six gates make the generators irrelevant to trust —
among them the byte-tie, which re-assembles the binary image from the certificates. The output is a
static Linux executable with no libc, no runtime and no C.

| part | shape at the end |
|---|---|
| kernel | `kernel/`, about 27k lines of shard on a 4k-line Rust interpreter, decision procedures inside it |
| trusted | the interpreter, the checker's sources, 15 axioms, per-binary axioms, the models' fidelity (tested) |
| proofs | its own language: `claim`, `requirement`, `fulfills`; goals are conditional ∀-equations |
| pipeline | spec ⊑ imp (`models/imp`, a target-neutral machine) ⊑ a program of the x86 model, then bytes |
| compilers | `tools/impc` from spec to imp; `models/imp/to_x86.shard` from imp to x86; older ones frozen |
| targets | x86-64 Linux (binaries run on silicon); wasm (run in V8); RISC-V (in qemu); RP2350 PIO |
| tools | `prove` (auto-prover), `search` (proof search), `shardfmt`, `build`, `canon`, `digest` |

## 2. What it reached

- **A proven fast binary.** `sha256sum` as a streaming executable that picks hardware-accelerated or
  scalar code by a proven CPU-feature dispatch, its contract met with no condition left: 0.626 s/GiB,
  1.08× coreutils as shipped, 1.01× openssl. Its scalar variant is 6.1× slower than coreutils with
  the hardware path masked: seven times the instructions, every temporary spilled to memory (no
  register allocation).
- **Small binaries through all six gates** (`./addw 2 3` prints 5 from a 728-byte executable);
  `snake_game_3`, a game whose I/O contract is met; a proven standard library from integers to floats
  and sha256.
- **Two finished parts of the compile proof** (§5): the theorem from the intermediate machine to x86
  (905 claims) and the runtime's laws (1,070 claims). A 13-function test program compiled by `impc`
  matches its specification on silicon, 15 runs of 15, compared by exit status.
- **Proof size.** Explicit conversion cut the restated part of sha256's machine proofs 5.5×
  (43,451 → 7,969 lines). The proof-search engine closes 172 of a 182-goal benchmark.

## 3. What worked

- **Machines as libraries.** A target and the operating-system boundary are ordinary functions. The
  kernel never learns a target, and "compiled correctly" is a theorem about a value.
- **Untrusted generators, trusted gates.** Anything may propose a lowering; only the gates decide.
- **One neutral intermediate machine.** imp holds the memory story once. From imp to a machine is
  only instruction selection, the same for every program because imp's scalars are typed.
- **Prove once, compute per program.** A validator (`compile p = m` plus one soundness theorem) makes
  each program's proof one computation and one citation.
- **Honest limits.** Machine limits are premises or declared failures: overflow, memory, stack.
- **A counted heap with a ghost.** Exact reference counts, no tracing collector, laws stated over an
  abstract list of live cells. A failed optimization proof costs speed, never soundness.
- **The measure is the induction.** A function's termination measure is the induction of its
  certificate, so hand-written and generated code meet one theorem shape and compose.
- **Contracts and a trust ledger.** Review reads interfaces and `requires` lists; each axiom a binary
  rests on is listed with its kind; each soundness hole found is pinned by a test.

## 4. What did not work, and why it was replaced

- **Certificate volume.** The rewriter matches syntax only, so proofs spell out whole machine states
  and exact step counts. About 45% of the repository was generated certificates. The machine theorem
  is 173,604 lines, mostly generated; the runtime's laws take 71,652 lines for a 295-line runtime; a
  25-statement function's certificate is 1,148 lines.
- **A separate proof language of equations.** No ∃, no dependent types, no statements about
  functions. Existentials became ghost "twin" evaluators, extractor functions and towers of fuel.
- **Holes in a hand-built kernel.** Decision procedures sat inside the kernel. Six proofs of `0 = 1`
  were found in 2026, all in special rules, dispatch tables or gates that read text. There was no
  outside oracle to compare against.
- **Speed was hand work.** The fast path is a hand-written accelerated module and a 29k-line
  hand-written imp program (71× its specification). The generic path compiled only the 13-function
  test, and proof search closed none of its certificates.
- **Trust left open.** The Rust interpreter is trusted; the fast checker was built through C,
  unproven.
- **Never finished.** Generic-path binaries of `calc` and `shardfmt`, the composition with the World
  (§5), register allocation, RISC-V binaries.

The owner, on replacing it: "the existing kernel has some properties that reflect the early MVP
nature of what we tried to build first"; the bar for its successor is "parity with Lean". V3 answers
with Lean 4's kernel rules exactly, three axioms where there were fifteen, and one logic for programs
and proofs.

## 5. The compile proof as v2 left it

The claim for a binary: its system-call trace and exit status are what the specification program does
to its World (the I/O state it threads), or it stops with a declared failure. A readback maps memory
and a machine word to the value they represent. The claim splits into four parts.

| part | what it says | state |
|---|---|---|
| spec ⊑ imp, per function | on a heap meeting the invariant, with arguments that read back, the result reads back as `f(args)` or fails as declared; by induction on the function's measure | six written by hand; the generator that would write them was not started |
| the runtime's laws | allocate, fill and seal a cell, increment, release — each keeps the heap invariant | complete |
| imp ⊑ x86 | one theorem for every well-typed imp program; per program, compute the translation and cite it | complete |
| composition with the World | the machine's system-call trace matches the specification's World | not started |

V3 has re-proved two of the six per-function results in its own logic, with the runtime's laws as
stated assumptions (`v3/models/imp`).

The owner's rulings on it. Hand-lowering is to be approximately zero, as a gate: a program the
compiler refuses is a compiler bug. The order: "A -> C2b -> B sounds good" (machine theorem, runtime
laws, per-function). One verified-compiler theorem over the compiler as data was rejected because it
needs a reflection theorem nobody had priced; when a hand certificate later passed the 300-line
trigger set for reopening that question, the owner kept it shut. Ghost twins (functions computing the
heap a call leaves): "option 1 sounds reasonable".
